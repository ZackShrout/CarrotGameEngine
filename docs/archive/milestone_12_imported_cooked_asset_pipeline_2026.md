# Carrot Game Engine - Milestone 12

**Last Updated:** April 13, 2026
**Title:** Imported Cooked Asset Pipeline
**Status:** Complete
**Focus:** Introduce engine-owned imported/cached asset artifacts such as `.ctex`, `.caud`, `.csprite`, `.cmap`, and related cooked formats so Carrot can avoid repeated expensive import work while preserving JSON-authored source-of-truth asset definitions.

Archived in April 2026 after the imported/cooked asset pipeline landed in the engine with shared invalidation, cache regeneration, and first binary cooked formats across multiple asset classes.

---

## Closeout Summary (April 13, 2026)

Milestone 12 is now considered complete.

Delivered outcomes:

* shared imported-artifact cache infrastructure with deterministic invalidation based on authored manifests, source dependencies, importer version, and cooked format version
* automatic load-or-regenerate behavior for stale or missing cooked artifacts
* first binary cooked low-level asset formats:
  * `.ctex`
  * `.caud`
* binary cooked higher-level imported asset formats:
  * `.csprite`
  * `.cmap`
* authored JSON remaining the source of truth while cooked artifacts stay machine-generated engine-owned outputs
* regression coverage for cooked artifact round-trips, manifest metadata wiring, regeneration, and cache reuse

Out of scope by design (deferred):

* packaging/distribution bundles
* encrypted or protected asset containers
* editor-driven cook daemons or build-farm orchestration
* scene-level cooked formats

---

## Milestone Goal

Carrot's current asset architecture is strong in structure:

* source files are distinct from authored asset definitions
* runtime loaded assets are distinct from authored JSON
* importers and loaders are intentionally separated

However, the engine is now large enough that repeated import/load cost is becoming a real usability issue.

This milestone introduces a proper imported/cooked cache layer:

* machine-generated
* engine-owned
* invalidated from authored inputs
* loaded when valid
* regenerated when stale or missing

The goal is not to replace JSON asset definitions.
The goal is to make them practical at scale.

---

## Scope Summary

Milestone 12 is **not**:

* a final packaging/distribution system
* a monolithic opaque asset database
* an editor-only import workflow
* a demand for all asset types to be cooked immediately
* an excuse to blur authored data and imported cache data

Milestone 12 **is**:

* a first-class imported/cached artifact layer
* asset fingerprinting and staleness detection
* load-or-regenerate behavior
* better startup/load-time characteristics
* a foundation for future packaging and tool workflows

---

## Milestone Relationship

Milestone 12 is the general imported/cooked asset milestone.

That means:

* Milestone 11 may introduce `.cfont` first as a text/UI-enabling cooked artifact
* Milestone 12 should absorb the lessons from that work into a broader, reusable imported-artifact architecture
* Milestone 12 should avoid taking ownership away from the UI/text milestone for the initial `.cfont` delivery

This keeps the work split clean:

* Milestone 11 proves one real consumer-driven cooked artifact path
* Milestone 12 generalizes the architecture for the rest of the asset pipeline

---

## Why This Milestone Comes Next

Carrot has now crossed the point where live re-importing everything every time is no longer just a harmless early-engine cost.

Current pain points:

* meaningful load time during asset-heavy bring-up
* repeated decoding/import work for assets whose authored data has not changed
* no persistent engine-native derived outputs despite an explicit importer/loader split

This milestone addresses that ceiling while staying aligned with the asset architecture already described in the docs.

---

## Design Principles

### 1. Authored JSON Remains the Source of Truth

Cooked/imported artifacts must remain derived outputs.

The source of truth remains:

* source media
* authored asset definition JSON

### 2. Imported Artifacts Are Engine-Owned

Formats such as `.ctex`, `.caud`, `.csprite`, `.cmap`, and `.cfont` are not user-authored files.
They are machine outputs generated by Carrot importers.

### 3. Validity Must Be Deterministic

Artifact reuse must be gated by explicit validity checks such as:

* authored asset definition fingerprint
* referenced source dependency fingerprint
* importer/schema version
* cooked format version

### 4. Regeneration Must Be Automatic

If an artifact is missing or stale, Carrot should regenerate it rather than forcing manual cleanup as the primary workflow.

### 5. Rollout Should Start With High-Value Asset Types

This milestone should start where the practical wins are strongest:

* textures
* audio

Then expand to:

* fonts where needed by the runtime UI/text pipeline
* sprites
* tilemaps

Scene-level cooked outputs can follow once the lower-level asset path is stable.

`.cfont` is expected to be introduced by the native MSDF text/UI milestone as a direct enabler for runtime UI text.
Milestone 12 should ensure that the broader imported-artifact architecture is general enough to encompass `.cfont` cleanly, even if `texture` and `audio` remain the primary first implementation slice here.

---

## Definition of Done (Milestone-Level)

Milestone 12 is successful when all of the following are true:

1. Carrot supports at least one real imported/cooked asset format end-to-end.
2. The engine can detect whether a cooked artifact is valid, stale, or missing.
3. The engine can regenerate stale/missing artifacts automatically from authored definitions.
4. The authored JSON layer remains the source of truth and is not replaced by cooked files.
5. The asset pipeline docs and runtime behavior clearly separate authored assets, imported artifacts, and runtime loaded assets.

---

## Ticket 1 - Introduce Imported Artifact Layer and Terminology

**Priority:** P0
**Outcome:** The asset system formally recognizes imported/cooked artifacts as a distinct pipeline layer.

### Why

The architecture should be explicit before formats and code start accumulating.

### Scope

Define and implement the engine-side concept of imported artifacts, including:

* terminology
* storage/root strategy
* artifact metadata/header expectations
* versioning ownership

### Acceptance Criteria

* The code and docs clearly distinguish authored definitions from imported artifacts.
* Imported artifact handling has an engine-owned abstraction rather than ad-hoc file writes.
* The chosen artifact location strategy is documented and intentional.

---

## Ticket 2 - Fingerprinting and Staleness Detection

**Priority:** P0
**Outcome:** Carrot can tell whether a cooked artifact is reusable.

### Why

Without deterministic validation, cache reuse becomes fragile and unsafe.

### Scope

Introduce validity checks based on some combination of:

* asset definition contents or hash
* source dependency timestamps or hashes
* importer version
* cooked format version

The exact mechanism can evolve, but it must be reliable and explicit.

### Acceptance Criteria

* The engine can classify an artifact as valid, stale, or missing.
* A changed asset JSON invalidates the prior artifact.
* A changed referenced source file invalidates the prior artifact.

---

## Ticket 3 - First End-to-End Cooked Formats: `texture` and `audio`

**Priority:** P0
**Outcome:** Carrot gets real load-time wins on the highest-value early asset types.

### Why

Textures and audio are the best first proof because they are common, meaningful, and already have clear importer/loader boundaries.

### Scope

Implement first-pass imported artifact support for:

* `*.ctex`
* `*.caud`

Milestone coordination note:

* `.cfont` may already exist by the time this milestone lands, or may land in parallel through the runtime UI/text milestone
* this milestone should reuse the same imported-artifact architecture rather than treat fonts as a special one-off path

Likely responsibilities include:

* importer writes artifact
* loader prefers valid artifact
* fallback path regenerates when needed

### Acceptance Criteria

* Texture and audio assets can load from valid imported artifacts.
* Missing/stale artifacts regenerate automatically.
* Runtime behavior remains correct whether loading from fresh import or cached artifact.

---

## Ticket 4 - Extend the Path to `sprite` and `tilemap`

**Priority:** P1
**Outcome:** Higher-level authored assets can participate in the same imported pipeline.

### Why

Once the low-level path is stable, the next biggest wins come from richer authored assets.

### Scope

Design and implement imported/cooked support for:

* `*.csprite`
* `*.cmap`

This should preserve the existing authored contracts while avoiding repeated expensive import work.

### Acceptance Criteria

* Sprite and tilemap artifacts can be generated and loaded through the same validity model.
* Existing authored JSON remains unchanged as the user-facing source of truth.
* Higher-level cooked support builds on the same shared infrastructure, not a second ad-hoc path.

---

## Ticket 5 - Runtime and Tooling UX for Cache Regeneration

**Priority:** P1
**Outcome:** Imported artifacts improve the workflow instead of creating hidden confusion.

### Why

Even good cache systems become frustrating if their behavior is opaque.

### Scope

Add practical first-pass UX such as:

* clear logging about cache hit/miss/regenerate behavior
* bounded failure behavior when regeneration fails
* sensible handling when cache directories are absent

This should stay lightweight and engine-oriented.

### Acceptance Criteria

* Developers can tell whether an asset was loaded from artifact or regenerated.
* Missing cache state does not create a confusing failure mode.
* Regeneration failures surface clearly.

---

## Ticket 6 - Regression Coverage and Documentation

**Priority:** P1
**Outcome:** The imported pipeline is protected and understandable.

### Why

This system affects correctness, startup behavior, and future tooling direction.

### Scope

Add focused tests and docs for:

* artifact validity rules
* stale/missing regeneration behavior
* version-bump invalidation behavior
* first supported cooked asset types

### Acceptance Criteria

* Automated tests cover the first cooked pipeline behaviors.
* The asset pipeline docs describe the new imported artifact layer accurately.
* Future contributors can extend the system without guessing at the intended model.

---

## Out of Scope by Design

The following should stay out of Milestone 12 unless later explicitly approved:

* shipping/distribution packaging format design
* encrypted/protected asset bundles
* full content build farm or editor-driven import daemon
* “cook everything for every platform” orchestration
* replacing runtime asset IDs with cooked-path references

---

## Review Questions

These are the main questions this milestone document is intended to settle before implementation:

1. Where should imported artifacts live in the project/runtime model?
2. Should validity be timestamp-based, hash-based, or hybrid in the first pass?
3. What exactly belongs in the artifact header/metadata?
4. Which asset types should be in-scope for the first implementation slice versus later follow-up?

---

## Current Recommendation

If implementation started directly from this draft, the recommended first pass would be:

1. Define shared imported-artifact terminology, versioning, and storage rules.
2. Build fingerprinting/staleness detection.
3. Implement `texture` and `audio` as the first broad asset-pipeline slice.
4. Reuse the same architecture for `sprite`, `tilemap`, and any existing/parallel `.cfont` work rather than branching into special-case paths.
