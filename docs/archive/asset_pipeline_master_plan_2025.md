# Asset Pipeline Master Plan

## Purpose

Define a clean, scalable asset authoring → import → registry → runtime pipeline that works **without an editor today** and **with an editor later**, while guaranteeing **fast, cache-friendly runtime access**.

This document is the contract for how *all* engine assets (audio, textures, sprites, animations, models, etc.) are identified, imported, stored, and accessed.

---

## Core Principles

1. **Assets are immutable at runtime**

    * Assets are never mutated in place.
    * Replacement (via re-import) is the only way assets change.

2. **Runtime access is handle-based and O(1)**

    * No strings, maps, or parsing on hot paths.

3. **Import separates intent from execution**

    * Authoring formats are flexible.
    * Runtime formats are rigid and minimal.

4. **Editor is a frontend, not a dependency**

    * Same pipeline works with JSON today and UI later.

---

## Asset Identity

### Authoring Asset ID (Human-Facing)

* UTF-8 string
* Hierarchical
* Namespaced by asset type

Examples:

```
audio.music.world_map
audio.sfx.footstep.grass
texture.ui.button.normal
sprite.player.run
```

Properties:

* Stable
* Readable
* Diff-friendly
* Editor-friendly

---

### Runtime Asset ID (Engine-Facing)

```cpp
using asset_id = uint64_t;
```

* Generated by hashing the authoring asset ID
* Computed once during import
* Stored, not recomputed
* Collisions detected and rejected during import

---

## Asset Handles

Handles are the only thing game code holds.

```cpp
struct asset_handle
{
    uint32_t index;
    uint32_t generation;
};
```

* Type-specific aliases (e.g. `audio_asset_handle`)
* Opaque
* Cheap to copy
* Detects stale references

---

## Asset Registry Guarantees

Each asset registry guarantees:

1. O(1) lookup by handle
2. Contiguous storage per asset type
3. Immutable assets after load
4. Read-only thread safety
5. Stable handles for the session
6. Explicit failure on invalid access
7. No runtime allocations on lookup

---

## Three-Layer Asset Architecture

### 1. Authoring Layer (Human-Facing)

* JSON (current)
* Editor UI (future)
* C++ descriptors (optional / early dev)

Characteristics:

* Flexible
* Readable
* Slow
* Never used on hot paths

---

### 2. Import Layer (Engine-Facing)

Responsibilities:

* Parse authoring data
* Validate schemas
* Resolve references
* Apply defaults
* Normalize values
* Produce runtime assets

Import may occur:

* At startup (current)
* Offline (future)
* Via editor (future)

---

### 3. Runtime Layer (Hot Path)

Characteristics:

* POD or near-POD
* No strings
* No maps
* Cache-friendly
* Deterministic

Only this layer is visible to runtime systems.

---

## Importer Interface (Conceptual)

```cpp
struct asset_import_context
{
    file_system& fs;
    asset_registry& registry;
    log_sink& log;
};
```

Each asset type provides an importer:

```cpp
struct audio_asset_importer
{
    bool import(asset_import_context& ctx,
                const authoring_node& node);
};
```

Importers:

* Know authoring formats
* Produce runtime assets
* Do not touch runtime systems

---

## Audio Asset Authoring Schema (JSON)

```json
{
  "id": "audio.music.victory",
  "sample": "Audio/Victory.wav",

  "bus": "music",

  "gain": 1.0,
  "gain_variance": 0.0,

  "pitch": 1.0,
  "pitch_variance": 0.0,

  "spatial": "none",

  "loop": {
    "start": 0,
    "end": 0
  }
}
```

Notes:

* Authoring schema is expressive and extensible
* Defaults applied during import

---

## Runtime Audio Asset (`sound_asset_t`)

```cpp
struct sound_asset_t
{
    audio_sample_handle sample;

    audio_bus_id bus;

    float gain;
    float gain_variance;

    float pitch;
    float pitch_variance;

    spatial_mode spatial;

    distance_model distance;
    float min_distance;
    float max_distance;

    uint32_t loop_start_frame;
    uint32_t loop_end_frame;
};
```

This structure:

* Is immutable
* Contains no authoring data
* Is safe for audio-thread use

---

## Summary

This pipeline:

* Works today without tooling
* Scales cleanly to editor-driven workflows
* Keeps runtime fast and predictable
* Applies uniformly to all asset types

Audio assets serve as the pilot implementation for the engine-wide asset system.
